`.env.local` (gitignored, repo root) already contains, among others:

  KV_REST_API_TOKEN=<bearer token>
  KV_REST_API_READ_ONLY_TOKEN=<bearer token>
  KV_URL=..., REDIS_URL=...

The Upstash REST contract was verified live during planning:
  POST $KV_REST_API_URL
  Authorization: Bearer $KV_REST_API_TOKEN
  Content-Type: application/json
  body: a JSON array whose first element is the command name, e.g. ["PING"]
  response: {"result": <value>}   e.g. {"result":"PONG"}  (HTTP 200)
This array-body form is what `scripts/push_redis.py` must use — one command per request.

Local Python is 3.9.6 (system python3); CI pins 3.12. The script must run on BOTH,
so use `from __future__ import annotations` for any `X | None` style annotations
(this is exactly what `pipeline/fetch_and_curate.py:49` already does).

Pipeline conventions to mirror (pipeline/fetch_and_curate.py):
  - stdlib HTTP only: `urllib.request.urlopen` / `urllib.request.Request`. NO `requests`, NO `@upstash/redis`.
  - module-level SCREAMING_SNAKE_CASE config constants at the top of the file
  - private helpers prefixed with a single underscore (e.g. `_first_number()`)
  - type hints on every function signature
  - double-quoted strings, f-strings for interpolation, 4-space indent
  - Spanish comments/docstrings
  - warnings go to stderr as `Aviso: ...`; `sys.exit("<mensaje>")` is reserved for missing required env vars

Canonical schema (STACK.md "KV Storage Schema", locked by CONTEXT.md "Claude's Discretion"):
  HSET push:subscriptions <sha256hex(subscription.endpoint)> <compact JSON of subscription>
  read-all  -> HGETALL push:subscriptions   (single command, never KEYS/SCAN — PITFALLS Pitfall 7)
  delete    -> HDEL  push:subscriptions <sha256hex(endpoint)>
The stored value is exactly `PushSubscription.toJSON()`:
  { "endpoint": string, "expirationTime": null|number, "keys": { "p256dh": string, "auth": string } }
which is also exactly what `webpush.sendNotification()` takes as its first argument in Phase 3 —
so nothing is reshaped between storage and send.

    - `put(subscription: dict) -> str` — validate the shape first (must have a non-empty string

      `json.dumps(subscription, separators=(",", ":"), sort_keys=True)`, `HSET` it under its endpoint
      field, and return the field.
    - `get(endpoint: str) -> str | None` — `HGET` by endpoint field, returns the raw stored JSON string.
    - `list_all() -> dict` — a single `HGETALL`, returning the field→JSON-string map.
    - `delete(endpoint: str) -> int` — `HDEL` by endpoint field, returns the number removed.
    - `selftest() -> int` — see Task 2 for the exact behaviour it must implement.

    CLI dispatch via `if __name__ == "__main__":` reading `sys.argv`, supporting exactly these
    subcommands: `put <path-to-subscription.json>`, `get <endpoint>`, `list`, `del <endpoint>`,

    endpoint, not the full JSON, so `p256dh`/`auth` key material is not casually dumped to a terminal).
    Unknown subcommand or wrong arg count -> print usage to stderr and exit 2.

    Never hardcode a URL or token in the file. Never print the value of `KV_REST_API_TOKEN`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| local/CI shell → Upstash REST API | A long-lived bearer token (`KV_REST_API_TOKEN`) grants full read/write on the whole Redis database over HTTPS |
| stored subscription data → future send path | `keys.p256dh` + `keys.auth` are per-device encryption material; anyone holding a stored subscription record can push arbitrary notifications to that device |
| client-supplied subscription JSON (Phase 2) → this storage layer | Untrusted shape crosses into Redis; validation must live at the storage boundary, not in the UI |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Information Disclosure | `scripts/push_redis.py` | mitigate | Token and URL are read from `os.environ`/`.env.local` at runtime only; Task 1 verify greps the file and fails if any `upstash.io` hostname or bearer-token-shaped literal is hardcoded |
| T-02-02 | Information Disclosure | `list` subcommand output | mitigate | `list` prints only `<field>\t<endpoint>`, never the stored `p256dh`/`auth` key material, so casual debugging cannot leak per-device push credentials into terminal scrollback or CI logs |
| T-02-03 | Tampering | subscription records written to Redis | mitigate | `put()` validates that `endpoint`, `keys.p256dh` and `keys.auth` are non-empty strings before any `HSET`, rejecting malformed/malicious objects at the storage boundary (PITFALLS "Security Mistakes" row 4) — this is the gate `api/subscribe.js` will reuse in Phase 2 |
| T-02-04 | Denial of Service | Upstash free-tier command budget | mitigate | Enumeration is a single `HGETALL`; `KEYS`/`SCAN` are forbidden and the Task 1 verify fails the build if they appear (PITFALLS Pitfall 7). Selftest cleans up after itself so no dead records accumulate |
| T-02-05 | Elevation of Privilege | `KV_REST_API_TOKEN` vs `KV_REST_API_READ_ONLY_TOKEN` | accept | The CLI needs write access for `put`/`del`, so it uses the read-write token. The read-only token is left available for any future read-only consumer; scoping further would require a second Upstash resource for no security gain at this scale |
| T-02-SC | Tampering | package installs | mitigate | This plan installs nothing — stdlib-only Python, zero npm/pip packages, no `package.json`. Supply-chain surface for this plan is empty by construction; the phase-wide `npx` legitimacy gate lives in plan 01-01 (T-01-SC) |
</threat_model>
