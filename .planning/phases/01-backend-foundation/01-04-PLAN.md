<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → local filesystem | A captured `PushSubscription` (endpoint + `p256dh` + `auth`) is written to a repo-root file; that file is enough for anyone holding it to push arbitrary notifications to the developer's device |
| local shell → Google/Mozilla/Apple push service | `web-push` signs a VAPID JWT with the private key and posts an encrypted payload to a third-party endpoint |
| local shell → npm registry | `npx --yes web-push` downloads and executes code before every send |
| local shell → Upstash Redis | The real subscription is written into the production `push:subscriptions` hash during the test |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-01 | Information Disclosure | `push-test-subscription.json` | mitigate | Task 1 adds an explicit `.gitignore` rule and the verify asserts `git check-ignore -q push-test-subscription.json` exits 0; Task 3 step D deletes the file, and the plan-level verification re-asserts its absence |
| T-04-02 | Information Disclosure | terminal output of `send-test-push.sh` | mitigate | The script is specified to never echo VAPID_PRIVATE_KEY, KV_REST_API_TOKEN or the subscription `auth` value; VAPID flags are passed as argv from environment variables rather than being printed |
| T-04-03 | Tampering | production `push:subscriptions` hash polluted with a developer test record | mitigate | The record is written and then explicitly removed by `--cleanup`; Task 3 acceptance and the plan-level verification both assert `push_redis.py list` shows no residue, so Phase 3's first real send does not target a stale developer device |
| T-04-04 | Spoofing | VAPID key mismatch surfacing only at the first real daily send | mitigate | This plan exists specifically to force a real signed send now; a 401/403 is called out in the checkpoint instructions as the diagnostic for a mismatched pair (PITFALLS Pitfall 1) |
| T-04-05 | Information Disclosure | push payload content | accept | The body is public sector-narrative text already shown on the homepage; REQUIREMENTS.md rules out personalised digest content entirely, so no private data can enter a payload |
| T-04-SC | Tampering | `npx --yes web-push` supply chain | mitigate | Covered by the blocking-human legitimacy gate in plan 01-01 (T-01-SC), which explicitly approves `web-push` for both `generate-vapid-keys` and `send-notification`. No new package is introduced here, and no `package.json`/`node_modules` is committed |
</threat_model>
